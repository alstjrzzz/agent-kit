## README 작성

프로젝트를 처음 보는 사람이 뭘 하는 프로젝트인지, 어떻게 실행하는지 빠르게 파악하게 하는 문서다. 가독성이 중요하므로 불필요한 정보는 과감하게 제외하여 간결하게 작성한다.

### 톤

- 평서형 "~다"체로 쓴다. 존댓말은 쓰지 않는다.
- 문장 짧게, 한 문장에 정보 하나만. 길어지는 문장은 두 문장으로 쪼갠다.
- "정말", "매우", "굉장히" 같은 의미 없는 강조 부사를 뺀다.
- AI 특유 클리셰("오늘은 ~", "그야말로" 등), 이모지, 과한 배지 나열은 쓰지 않는다.
- 엠대시(—)는 쓰지 않는다.
- 볼드는 최대한 쓰지 않는다.
- 실제로 안 쓰는 조어를 만들어내지 않는다. 업계에서 통용되는 표현이 있으면 그걸 쓰고, 없으면 알아서 명확한 쪽으로 판단해서 쓴다.
- 파일 경로, 명령어, 예시 코드에는 한글 플레이스홀더를 쓰지 않는다. 실제로 있을 법한 영문 이름을 쓴다.

### 문단

- 문단은 2~4문장 정도로 짧게 쓰고, 문장은 자연스럽게 이어 쓴다. 문장마다 억지로 줄을 끊지 않는다.
- 다른 이야기로 넘어갈 때만 빈 줄로 문단을 나눈다.

### 요약 수준

- 예시나 부연설명은 꼭 필요한 것만 추리고 나머지는 뺀다.
- 분량은 고정하지 않고 그 내용이 실제로 필요로 하는 만큼으로 정한다. 그래도 가독성과 간결함이 기본값이다.

### 구조

- 프로젝트 성격에 따라 가감하되, 보통 이 순서를 따른다: 프로젝트 이름과 한 줄 설명, 주요 기능(불릿 3~6개), 기술 스택, 설치 및 실행 방법, 사용 예시, 프로젝트 구조, 라이선스.
- 개인 사이드 프로젝트처럼 기여자 가이드나 라이선스가 불필요하면 그 섹션은 뺀다.
- 설치/실행 명령어는 실제로 그대로 실행 가능한 것만 코드블록에 넣는다. 검증 안 된 명령어를 추측해서 채우지 않는다. 의존성 설치, 환경변수 설정, 실행 명령을 순서대로 분리한다.
- 프로젝트 구조는 트리로 보여주되 실제 폴더 구조를 반영한다. 지어내지 않는다. 전체를 다 보여줄 필요는 없고 핵심 디렉토리 위주로 추린다.
- 아키텍처나 흐름처럼 다이어그램으로 표현 가능한 내용은 mermaid 코드블록으로 그려 넣는다. mermaid로 안 되는 스크린샷이나 실제 이미지가 필요한 자리는 `[이미지: 설명]`으로 표시해둔다.
- 표를 쓸 때는 같은 열끼리 문체와 분량을 맞춘다. 한 행만 장황하게 쓰지 않는다.
- 예시 경로나 값은 `<your-project-path>`처럼 채워 넣을 자리가 명확한 placeholder를 쓴다. 그럴듯한 가짜 값을 쓰지 않는다.
- 아직 만들어지지 않은 기능이나 항목을 예시로 쓸 거면 "추가 예정" 등으로 명시한다.
- 같은 내용을 여러 섹션에 중복 설명하지 않는다. 가장 적절한 자리 한 곳에만 적는다.
- 코드 예시가 여러 개 나열될 때, 설명을 코드블록 밖에 따로 두면 미리보기에서 어느 블록 설명인지 헷갈릴 수 있다. 짧은 설명이면 코드블록 안 주석으로 묶는 것도 방법이지만, 항상 그래야 하는 건 아니고 상황에 맞게 판단한다.

### 작성 전에

- 프로젝트 코드나 설정 파일이 있으면 먼저 읽어서 실제 기술 스택, 실행 명령, 구조를 확인한다. 추측해서 쓰지 않는다.
- 이 프로젝트 성격에 어떤 섹션 구성이 맞는지 먼저 판단한다. 정해진 틀에 억지로 맞추지 않는다.
- 정보가 부족하면(라이선스 종류, 배포 방식 등) 채워 넣지 말고 사용자에게 묻는다.

### 출력

`README.md` 파일로 저장한다.
